# SAGE

**Semantically Aligned Generation and Equivalence**

SAGE translates bounded scientific software to Rust or modern C++ and records reproducible behavioral comparisons
between the original implementation, the translation, and an independent NumPy reference.

Campaign generation uses **only new SymSan-generated cases**. API replay can reuse authenticated
generated corpora; it never labels a replay sweep as new solver output. Bootstrap inputs initialize the solver but are
never executed as validation evidence. Unchanged seeds, duplicate generated bytes, and malformed
inputs are excluded. Missing instrumentation, disabled generation, timeouts, and empty corpora cannot
produce a passing run. A completed campaign with zero valid generated cases reports `NO_TEST_CASES`.

Passing reports describe sampled agreement, not formal verification or universal equivalence.

The separate [bounded formal proof pilot](docs/formal-verification.md) uses `sage prove`
to check the pinned HPTT scalar copy/transpose kernel and the checked-in Rust Tensor
operations against the same exact specification for dimensions 1–4. This kernel-level
proof has explicit assumptions and exclusions. It does not change the conservative
full-library compatibility gate or turn SymSan campaigns into formal proofs.

The [six-operation extension](docs/tensor-six-proof.md) proves 144 public Tensor
obligations in each language using exact ordered-expression semantics. The public
CPU/Python dispatchers route the bounded float64 domain to these methods; exact-bit
adapter replay and six source-fault detections/native replays per language accompany
the proofs. See the [current evidence](artifacts/tensor-six/report.md).

The independent [modern C++20 translation](ports/einsums-cpp/README.md) now implements
the broad CPU/Python library surface. Its new 23-operation campaign passes 128 fresh
SymSan cases; the saved API corpus records 15,872 checks, including 2,056 documented
reference disagreements. The original six-operation profile remains available and
its 32 paired copy/transpose proof obligations retain their bounded kernel scope.
See [scope and evidence](docs/modern-cpp.md); the broad API is not formally proved.

Current project presentations live in [artifacts/sage-slides](artifacts/sage-slides/README.md).
Its `output/` folder contains the latest overview and technical decks in PPTX and PDF formats.

## Einsums CPU and Python library scope

The target is the pinned Einsums v1.1.5 CPU and Python library at commit
`22a115978041e905461b24d9ca2a17bfcce01f32`; HIP/GPU is excluded.

The independent [Rust port](ports/einsums-rs/README.md) and
[C++20 port](ports/einsums-cpp/README.md), each with an installable Python package, cover
all 90 CPU exports of the compiled Python extension and its 16 public utility helpers. Numerical
APIs support float32, float64, complex64 and complex128. Implementations include tensors/views,
contraction plans, BLAS-style operations, factorizations, eigensystems, SVD, pseudoinverse, Lyapunov,
FFT, CP/weighted CP, Tucker/HOOI, block/tiled storage and HDF5. The Python imports are `einsums`
and `pyeinsums`; scientific arithmetic runs in the selected native backend. Install
the two packages into separate environments because their import names coincide.

**API presence does not establish exact upstream compatibility.** Mathematical corrections and
shape/layout differences are documented in [the API contract](docs/einsums-api.md). The conservative
full-library gate still reports `INCOMPLETE_SCOPE` until all required contracts and validation are
covered. It does not infer completion from passing bounded tests.

The original 23-operation campaign generates authentic SymSan inputs and runs upstream C++, Rust,
NumPy and the earlier Python ABI. The new API replay sweeps those authenticated inputs through
31 API groups in all four dtypes using the original compiled Python extension and the new Rust-backed
package. C++20 has its own native/Python campaign and the same 31-group replay.
SymSan instruments the **input decoder only**; neither run claims internal-library path
coverage. See [generation and replay commands](docs/einsums-api.md).

The previous six-operation profile remains available explicitly with `--config configs/einsums.yaml`.
See [the tensor-stage contract](docs/einsums-tensors.md).

## Setup and execution

Install Python 3.11+, `uv`, Rust, a C++20 compiler and Docker. The full C++ port also
requires CMake, Eigen 3.4+, nlohmann JSON 3.11+ and HDF5; see its build instructions.
The SymSan/Einsums environment runs as Linux amd64;
Apple Silicon uses Docker emulation. Image construction and upstream preparation require network
access. Validation containers run with networking disabled.

```console
uv sync --all-extras
make check
make build-containers
make build-einsums-container
uv run sage target prepare --target einsums
uv run sage run --target einsums --mode platform-demo --provider offline
```

The offline translation provider uses the checked-in Rust implementation and makes no API calls.
It still requires Docker and SymSan for validation. Unit and ordinary integration tests run without
Docker; orchestration tests explicitly stub generation and are not scientific campaign evidence.

The full-library profiles snapshot the checked-in multi-file Rust or C++ implementation.
Select C++20 with `make demo-cpp20-library`; Rust remains the default. The single-file
OpenAI provider remains available only for the earlier tensor profile; select it explicitly:

```console
OPENAI_API_KEY=<secret> SAGE_MODEL=<model> \
  uv run sage run --target einsums --config configs/einsums.yaml --provider openai
```

Each `runs/<run-id>/` captures source, translation, configuration, container identity, commands,
bootstrap seeds, generated corpus, executions, comparisons, operation counts, and Markdown/HTML
reports. Every discrepancy is replayed and saved with a `sage reproduce <directory>` command.
The CLI returns nonzero for empty, failed, partial, or discrepant campaigns.

## Other targets and scientific selection

Gau2Grid, DKH and GDMA remain potential-target catalog entries without runtimes or
bundled demonstrations. `configs/sage.yaml` has no target; pass Einsums
explicitly. Candidate state, technical implementation, and human pilot approval remain separate.

```console
uv run sage target list
uv run sage target show einsums
uv run sage target selection-status
uv run sage run --target einsums --mode scientific-pilot --selection decisions/<approved-decision>.yaml
```

Scientific-pilot mode requires a target-bound `APPROVED` decision with a human approver and time.
Platform-demo mode is available without creating a scientific selection.

The implementation and CLI live in the single `sage` package. Provider settings use `SAGE_MODEL`
and `SAGE_SAM_ENDPOINT`; upstream caches live under `.sage/`. Supported schema-1.0 and schema-1.1
run manifests remain readable. New campaigns use only SymSan-generated validation cases.

See [architecture](docs/architecture.md), [SymSan integration](docs/symsan-integration.md),
[target selection](docs/target-selection.md), and [the documentation index](docs/README.md).

## Repository contents

Source, tests, target catalogs, configuration, lockfiles, proof harnesses, curated
proof summaries and the current presentation files belong in Git. Local run
bundles, downloaded toolchains/upstreams, native binaries, virtual environments,
Python caches and private presentation builds are excluded by `.gitignore`.
Recreate them with the setup, build and verification commands above. Preserve
immutable raw run bundles separately when sharing proof or campaign evidence.

See [repository preparation](docs/repository-preparation.md) for a clean checkout
and validation workflow. The SAGE Python package uses Apache-2.0; the Rust and C++
ports retain their own MIT license files.
